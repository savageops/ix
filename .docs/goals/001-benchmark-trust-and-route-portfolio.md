# /goal — IX Perpetual Architecture Ascent

Advance IX through an unending sequence of finite, falsifiable, proof-bearing engineering rounds. Each round must deliver one named, measurable result for an IX user, agent, maintainer, or operator: a correct capability becomes usable, an incomplete path becomes complete, retrieval becomes materially better, execution becomes faster or lighter, failure becomes safer, or architecture becomes simpler in a way that accelerates future delivery. Operate on the whole repository when selecting and protecting that result, not by trying to improve every subsystem at once. Each invocation identifies the highest-value verified limitation, defines the before/after outcome, makes one coherent owner-aligned improvement, proves the result across its real blast radius, and ends with exactly one verdict: `PROMOTED`, `REJECTED`, `REVERTED`, or `BLOCKED`. IX is never declared complete, but every round must finish with a concrete delta rather than an inventory of activity.

IX is a native search and evidence engine whose quality emerges from the complete path between user intent and verified output. Raw matching speed matters, but so do query grammar, planning, candidate reduction, traversal, file identity, I/O policy, exact verification, concurrency, memory hierarchy, result assembly, context quality, protocol stability, platform behavior, build reproducibility, installation, recovery, and agent usability. Improvement means strengthening this system as a system. No local win may quietly weaken a neighboring stage, move cost into another phase, leave a surfaced command incomplete, or increase architectural entropy beyond the value it proves.

Results outrank ceremony. Research, competitor harvesting, architecture maps, refactors, tests, benchmarks, reviews, telemetry, reports, commits, and documentation are means of producing or protecting a result; none is itself the result unless the round explicitly targets that operator or maintainer capability. Do the minimum investigation needed to make the decision correctly, then build and prove the value. Stop a line of inquiry when additional detail cannot change the selected mechanism, implementation boundary, acceptance threshold, or verdict. Technical depth is mandatory where risk demands it and waste where it does not.

## Result contract

Before research or mutation, write the round in six lines: `Consumer`, `Current limitation`, `Result target`, `Baseline`, `Protected invariants`, and `Proof`. The result target names observable behavior, not an internal task: “installed MCP returns the same bounded search result as CLI” is valid; “review MCP code” is not. The baseline captures the present consumer outcome. Protected invariants name what may not regress. Proof names the shortest decisive user-path test plus any risk-driven supporting evidence. If these six lines cannot be written from current source and probes, the first bounded action is to obtain only the missing fact.

Select the next result by evidence-adjusted value: severity of the consumer limitation, number of consumers unblocked, correctness or trust risk removed, recurring time or resource saved, architectural leverage, probability of success, proof cost, and reversibility. Prefer completing or repairing a real surfaced path over speculative frontier work. Prefer a root cause that closes several observed failures over several local patches. Prefer a smaller result that can be installed and proven this round over a broad program that produces only analysis.

One round owns one result. Supporting changes may cross many files and layers when the blast radius requires them, but they must all serve the same before/after outcome. Do not opportunistically repair unrelated findings, run open-ended audits, or expand research because adjacent technology is interesting. Record valuable adjacent findings in the canonical queue with evidence and return to the active result. The architecture map determines what must be protected; it does not authorize simultaneous work on every mapped surface.

Use a result ladder to prevent local metrics from replacing product value. First preserve exactness, safety, freshness, deterministic behavior, and honest boundaries. Then prove the intended capability works through its canonical consumer and installed path. Then improve latency, throughput, memory, output economy, context quality, maintainability, or platform reach according to the round’s declared target. Optimize internal counters only when their causal connection to the selected result is demonstrated. A metric that does not alter consumer experience, operating cost, release confidence, or future delivery speed is diagnostic context, not a promotion axis.

Close every round with a compact before/after scorecard: consumer path; baseline result; candidate result; invariant and parity status; resource and performance status where relevant; complexity added and removed; installed-path status; unresolved risk; verdict; and next highest-value frontier. `PROMOTED` requires the target result to be materially achieved with hard invariants intact. `REJECTED` or `REVERTED` is successful learning only when it eliminates a strategy with reusable evidence and leaves no dead runtime complexity. `BLOCKED` requires an exact external condition and immediate continuation. Volume of code, research, tests, findings, or documentation never substitutes for the scorecard.

Source truth precedes direction, but reconnaissance is bounded by decision value. Establish checkout identity, governing contracts, dirty state, installed owner, and enough current runtime evidence to select the highest-value result. Then inspect only the source, history, ledgers, refs, tests, schemas, build surfaces, and probes that own or can falsify that result. Reconcile contradictions that could change selection or verdict; record unrelated drift without entering it. Memory, roadmaps, comments, attachments, prior reports, and this goal remain hypotheses until current source or execution confirms them. Use IX to inspect IX, and independently verify only critical claims.

Reconstruct the affected path as a connected pipeline before touching code; do not map unaffected pipelines. Use the applicable path: command `argv → compatibility lowering → typed invocation → dispatch → owner → output/error`; search `expression → strategy → roots → discovery/admission → index or cold route → I/O → specialist scan → exact verification → merge → projection`; persistent evidence `root identity → catalog/postings → delta → generation publication → reader pin → stale detection → reconciliation`; reading `path identity → bounded input → segmentation/windowing → coordinates → selection/compaction → omission accounting → projection`; release `refs → build → tests → qualification → atomic install → readback → rollback`. Trace the selected result through every stage that can change it and stop at proven boundaries.

Treat architecture as a portfolio of canonical owners. The CLI layer owns grammar, typed requests, compatibility translation, help, and completion contracts. Planning owns expression semantics, strategy choice, cost and route decisions before I/O. Discovery and admission own which paths enter work and must never create false negatives through an unsafe shortcut. Catalog, postings, generation, delta, and watcher owners form one persistent-index lifecycle. Scanner owners specialize literals, alternates, regex, structural search, casefolding, byte sharding, and platform I/O without duplicating final semantics. Merge and output owners preserve deterministic ordering, bounded retention, schema versions, sentinels, and continuation. `inspect`, `xo`, and `min` are distinct reading modes over shared identity, resource, coordinate, and serialization rules. CLI, agent output, and MCP are projections over canonical behavior, never parallel engines.

Study core code at algorithmic, microarchitectural, and memory-hierarchy levels together. For each hot path, identify asymptotic work, bytes touched, allocations, syscalls, branch shape, instruction footprint, cache residency, TLB pressure, sharing, scheduling, and tail behavior. For each cold/control path, optimize clarity, typed state, failure locality, and ease of proof. Preserve the no-mutex and no-allocation scan-loop invariants, bounded stack behavior, compile-time strategy selection, thread-local accumulation, exact final verification, and explicit `std.Io` flow unless stronger measured evidence justifies a replacement. Performance folklore, attractive assembly, or a route-local microbenchmark cannot authorize a change by itself.

Large core owners are architecture debt when they prevent local reasoning. Do not casually add another branch to an oversized file such as `src/core/search.zig`. First map the real responsibilities and data dependencies; move stable concepts behind narrow, typed, zero-cost boundaries only when the extraction reduces control-flow ambiguity without adding runtime indirection or duplicate ownership. Prefactor before feature work: make invariants visible, isolate pure planning from side effects, separate platform policy from shared semantics, and give tests a smaller owner to attack. File splitting by line count alone is cosmetic; split at domain and lifecycle boundaries.

Incomplete behavior is a standing priority lane. For the selected capability, build the smallest matrix needed to trace command tag through parser, typed request, dispatch, engine owner, output and error schema, help, completions, tests, docs, MCP/agent exposure where claimed, optimized build, and installed-path proof. Classify the affected surfaces as `complete`, `partial`, `boundary`, `debt`, `superseded`, or `unsupported`. A parser arm, enum tag, descriptor, test double, help entry, roadmap claim, telemetry field, or successful build is not completion. Either complete the canonical consumer path, narrow the public boundary honestly, or record the exact blocker and executable continuation.

Within the affected path, search for incompleteness beyond explicit `TODO` markers: no-op switches, listed-but-undispatched commands, schemas without runtime producers, `not_wired` fields, sleeping or silent platform fallbacks, masking skips, duplicated configuration, unreachable specialists, ignored options, and documentation or installation drift. Trace declaration → configuration → runtime merge → owner → side effect → readback → projection. Treat a broken link in the selected chain as its real capability state; queue unrelated findings without expanding the round.

Proof-carrying pruning is the semantic floor across cold and indexed execution. An accelerator may prioritize candidates. A mathematically safe negative may eliminate candidates. No heuristic, ignore policy, binary detector, cache, posting list, fingerprint, generated-file classifier, or learned ranker may suppress a possible match without an exhaustive-equivalence argument under its declared domain. No accelerator may manufacture a final match. Positive candidates pass the canonical exact verifier; uncertain negatives fail closed into a broader route. Every admission optimization carries adversarial parity fixtures and a brute-force oracle.

Resource governance is architecture, not a collection of command flags. CPU, memory, file handles, mapped bytes, I/O depth, worker count, output bytes, retained hits, context spans, index footprint, startup cost, and background work require typed ceilings and one precedence model. A sidecar has an independent declared budget and lifecycle; it may not make the foreground CLI appear light by exporting unmeasured cost. Backpressure, cancellation, partial failure, shutdown, stale-process cleanup, and recovery belong in the design before concurrency is widened. Measure peak and tail behavior, not only averages.

Platform nativeness means shared semantics over specialized backends. Windows, Linux, macOS, local disks, network filesystems, case-sensitive and case-insensitive volumes, symlinks and junctions, sparse files, long paths, invalid UTF-8, permission boundaries, interrupted reads, mmap differences, event loss, rename identity, and timestamp granularity all affect correctness. Select the strongest native I/O, event, scheduling, and memory primitive per target while preserving one conformance contract for matches, ordering, errors, freshness, fallback, and output. Unsupported runtime behavior is an explicit boundary with a safe fallback, never a silent capability claim.

The persistent index is one member of the architecture portfolio, not the product’s center. Its job is to reduce work without becoming a second truth engine. Generations are immutable and atomically published; readers pin one identity; event streams accelerate change discovery but cannot replace reconciliation; metadata narrows change detection while content evidence resolves ambiguity; overflow, reset, unsupported filesystem, or continuity loss triggers bounded repair or cold fallback. Index construction, compaction, delta overlay, query planning, freshness, storage, cleanup, and recovery must each have an owner and proof. A warm label without route, coverage, identity, and match parity is invalid.

Retrieval and context surfaces optimize evidence density while preserving source truth. Search finds exact occurrences. `inspect` returns exact bounded windows. `xo` selects query-guided context. `min` compacts a document without a query. Similarity and structural modes introduce their own evidence and dependency contracts. Evaluate these surfaces on coordinates, critical-fact and negation retention, redundancy, omission visibility, deterministic ordering, reconstruction cost, token/byte use, long lines, malformed input, and low-redundancy material. Development telemetry remains opt-in unless it changes the consumer’s next action.

Protocol surfaces are part of the core architecture. Text, JSON, agent projections, cursors, sentinels, exit codes, stderr, MCP, help, and completions must agree on command semantics while retaining format-specific framing. Schemas are versioned contracts, not formatting suggestions. Tool descriptors advertise only callable capabilities and teach correct use through precise names, parameter descriptions, closed inputs where practical, bounded defaults, read-only/idempotency annotations, structured errors, and output contracts. Test the same request through every claimed projection and compare semantic results, coordinates, truncation, continuation, and failures.

Build and dependency architecture must remain reproducible, inspectable, and network-free at build time. `.refs/index.md` owns provenance, commits, archive digests, licenses, local paths, and build-critical versus research-only status. `build.zig` owns compilation units, target features, optimization mode, linkage, generated-file aliases, and test artifacts. A successful incremental build is not clean-build proof; a linked executable is not runtime proof; a repository executable is not installed-owner proof. Verify supported targets and keep architecture decisions compatible with Zig’s actual compilation and ABI behavior rather than assumed language semantics.

Research is executable architecture. Before a consequential mechanism is selected, harvest source-bearing primary papers, specifications, maintainer-grade implementations, and issue or benchmark history across the relevant discipline. Reduce each candidate to workload, invariants, algorithm, data shape, traversal, resource behavior, failure mode, platform assumptions, and measured weakness. For every adopted source, record the decision it changes, capability it enables, weaker alternative it defeats, complexity it adds, license and provenance, and experiment that would falsify its value. A famous algorithm or theorem is vocabulary until IX proves its assumptions and transfer value.

Select work by evidence-adjusted architectural leverage, not novelty. Candidate lanes include semantic correctness, incomplete public behavior, owner consolidation, parser and planner coherence, discovery and admission, index lifecycle, scanner strategy, regex and structural engines, file-open and input policy, concurrency, memory hierarchy, merge and output, context quality, protocol parity, platform support, build provenance, deployment, tests, documentation truth, and operator recovery. Rank candidates by consumer impact, invariant risk, downstream leverage, proof cost, reversibility, and opportunity to make the system both better and simpler. Correctness and surfaced incompleteness normally outrank speculative optimization.

Performance safety is a gate on every relevant architecture change, not the goal’s sole axis. Freeze the installed champion, candidate hash, corpus, query, build, target, resources, route, cache state, match count, and output digest before interpreting time. Compare repository candidate directly with installed champion; use retained predecessors one at a time as historical regression sentinels, never as friendlier promotion baselines. Ripgrep datasets are representative workloads, not a required binary comparator. Preserve raw samples and distinguish process-cold, filesystem-warm, index-warm, setup, scan, merge, and output phases.

Treat performance as a vector: latency distribution, throughput, CPU time, instructions, IPC, branches, cache and TLB behavior, page faults, syscalls, allocations, peak RSS, mapped bytes, handles, startup, index cost, freshness lag, output bytes/tokens, and quality damage. Use paired alternating order, same-binary controls, independent repetitions, effect-size confidence intervals, non-inferiority margins, and causal profiling. A candidate promotes only when hard invariants pass, at least one predeclared consumer axis improves materially, protected axes remain inside frozen margins, and no important loss is hidden in an aggregate score. The approximate ten-percent boundary is an emergency ceiling per named soft metric, not an allowance and never applicable to correctness.

Validation follows the full blast radius. Prove parse and type contracts, unit behavior, integration flow, exact-oracle parity, adversarial and malformed inputs, deterministic repetition, concurrency schedules, resource ceilings, platform boundaries, recovery, schema fixtures, clean builds, optimized builds, benchmark identity, installation, and installed-path behavior as applicable. Tests are contracts: fix implementation defects rather than weakening assertions. A partial green suite remains partial. Skips, timeouts, flaky lanes, and historical failures are named and owned; they do not disappear behind a successful targeted test.

Each round follows one closed pipeline: define the consumer result; observe only enough repository and runtime truth to establish the owner, baseline, and risk boundary; map the affected architecture; freeze the hypothesis, target, invariants, falsifiers, regression surface, and rollback; harvest only decision-changing sources; prefactor only when needed to make the result safe and reviewable; implement one coherent slice; attack the relevant blast radius; prove the consumer result; run performance gates where the change can affect them; inspect the final artifact with a risk-proportionate maintainer-grade QC pass; decide; write the compact scorecard; commit only a proof-bearing improvement; promote only when installed-path gates pass; update the loop state; repeat.

Promotion is a release verdict, not a benchmark adjective. A promoted slice has one canonical owner, complete consumer behavior, deterministic and typed contracts, bounded resources, handled failure and recovery, applicable platform proof, clean source and dependency provenance, documentation parity, tests capable of detecting removal or regression, and installed-path evidence. A route-local gain with a whole-engine loss becomes a salvage investigation. A rejected experiment preserves the lesson and source evidence, not dead runtime code. A blocker names the exact external condition and first executable continuation.

Doctrine becomes machinery. Every durable belief seeks a code invariant, type, test, benchmark, telemetry field, documentation owner, and release gate. Every touched function explains its capability and why it exists. Every inline TODO closes in the same round or moves to the canonical durable queue with owner and trigger. Every round should reduce at least one form of entropy: duplicated ownership, oversized control flow, hidden fallback, stale claim, incomplete path, configuration split, unbounded resource, untested invariant, protocol drift, or unexplained performance debt.

The long-term architecture is a planner-led, proof-preserving engine that does the least necessary work at every layer: classify before I/O, prune only with safe evidence, choose the right execution tier, use platform-native primitives, keep hot loops flat and specialized, make persistent state immutable and recoverable, merge deterministically, emit only consumer-valued context, and expose identical semantics through every supported surface. Begin each invocation by asking which architectural link is currently weakest, what remains incomplete, what measurement could disprove the proposed repair, and whether the change improves the whole path rather than merely the code immediately in view.

## Reviewer mandate — protect the result

The reviewer is an independent adversarial results gate, not a stylistic reader of the submitted diff and not an invitation to reopen the entire repository. Begin with the declared result contract and try to disprove the claimed before/after improvement. Reconstruct the affected execution path from consumer input to observable result, then review only the owners whose invariants or contribution to that result can change. The diff identifies where mutation occurred; it does not define the blast radius, but the blast radius also does not justify unrelated archaeology. A change in query classification may require admission, routing, sharding, scanning, cache identity, output, and benchmark review; a local documentation change may not. Review depth scales with consequence, uncertainty, and reversibility.

The fourteen passes below are a coverage catalog, not fourteen mandatory research projects. Apply every relevant pass, mark irrelevant passes `N/A` with one-line reasoning, and stop when the result claim and its protected invariants are decisively proven or falsified. Findings are prioritized by their ability to change the current verdict. Adjacent debt that cannot change the current result is recorded for later rather than pulled into the round.

The first review pass proves scope and source truth. Record branch, HEAD, dirty state, candidate hash, installed hash, active compiler and target, build mode, enabled refs, relevant environment and configuration, current ledgers, active todos, public help, schemas, and executable behavior. Identify generated, vendored, backup, experimental, superseded, and installed artifacts before comparing code or binaries. Reconcile stale reports and contradictory status claims. Review cannot issue a clean verdict while the identity of the artifact, owner path, corpus, route, or governing contract is ambiguous.

The second pass proves capability completeness. For every capability touched or advertised nearby, trace command tag → parser → typed request → default and precedence merge → dispatch → engine owner → side effect or result → output and error serializer → help and completion → tests → docs and SKILL → MCP or agent projection where claimed → optimized build → installed path. Classify gaps rather than inferring intent. A listed MCP tool without a `tools/call` owner, an imported module without dispatch, a telemetry family left at `not_wired`, a platform branch that only waits, or a test-only path is review evidence of partial capability until runtime proof closes it.

The third pass proves canonical ownership and architectural fit. Locate every place the changed value is declared, derived, cached, copied, serialized, or independently defaulted. Reject split policy, parallel request construction, duplicated thresholds, shadow schemas, and output-specific business logic unless the separation is deliberate, typed, and tested. Ask whether the change belongs in the planner, admission proof, execution specialist, persistent lifecycle, resource policy, or projection layer. Prefer moving a decision to its real owner over adding another conditional to an orchestration file. Require any extraction from a large owner to preserve flat hot paths and compile-time specialization without creating allocation, indirection, or translation tax.

The fourth pass proves semantic equivalence across execution routes. Build a route matrix from expression shape, options, file type and size, index state, cache state, platform, output mode, resource pressure, and fallback trigger. Compare cold and warm, cache hit and miss, mmap and buffered, single-file and directory, serial and sharded, timed and non-timed, optimized and fallback, CLI and MCP, stable and streaming, stats-only and hit-producing paths. Every route must share the same exact match semantics or declare a narrower contract. Duplicate optimized loops are presumed drift risks until parity tests prove boundaries, overlap, casefolding, word behavior, long lines, invalid input, ordering, and counts.

The fifth pass attacks pruning and candidate formation. Inspect expression classification, trigram extraction, file admission, ignore handling, binary policy, hidden/protected paths, literal-alternate decomposition, posting-list intersection, block evidence, cached candidates, and generated-file shortcuts. For every negative decision, require the domain assumptions and exhaustive-equivalence proof. Test short needles, repeated trigrams, mixed `&&`/`||` boundaries, case-insensitive expansion, regex constructs outside the optimized subset, cross-chunk and cross-shard matches, rename and stale-index cases, and malformed or adversarial files. Any uncertainty must broaden to exact scanning rather than silently remove a candidate.

The sixth pass audits persistent identity and freshness as a transaction. Trace root normalization → filesystem identity → catalog entry → file metadata and content evidence → posting membership → generation manifest → atomic publication → reader pin → delta overlay → tombstone → stale rejection → reconciliation → cleanup. Prove which changes metadata can detect, where hashes or content evidence are required, how coarse timestamps, same-size rewrites, rename, overflow, journal reset, missed events, unsupported filesystems, process death, and partial publication are handled, and when cold fallback activates. A watcher or sidecar is an accelerator with an explicit budget and recovery contract; it is not permission to weaken query-time truth.

The seventh pass reviews the hot path at algorithmic, instruction, and memory-system levels. Identify bytes read and written, passes over data, allocations, syscalls, synchronization, branch structure, vector width, alignment, stack frame, cache working set, TLB behavior, prefetch utility, false sharing, and tail handling. Inspect generated assembly or profile evidence when the claimed mechanism depends on code shape. Confirm that diagnostic timing, counters, tracing, and attribution are disabled or measured symmetrically in qualification runs and do not insert extra clocks, branches, atomics, formatting, or cache pollution into only one candidate route.

The eighth pass reviews concurrency, boundedness, and lifecycle. Follow ownership of arenas, mapped regions, buffers, handles, worker contexts, thread-local reports, queues, shared generations, and background processes from creation through cancellation, join, flush, shutdown, crash, and cleanup. Test tiny and maximal ceilings, zero work, one giant file, many tiny files, slow storage, denied access, interrupted reads, output backpressure, and partial worker failure. Prove no mutex or allocation enters the scan loop, no hidden sidecar cost escapes the foreground budget, no worker outlives borrowed state, and deterministic merge survives schedule variation.

The ninth pass reviews platform semantics, not just compilation. Windows, Linux, and macOS implementations may use different discovery, open, mapping, event, affinity, and memory primitives, but must converge on the same match, ordering, freshness, path, error, and fallback contract. Review conditional compilation, ABI types, path normalization, separators, drive and UNC roots, case behavior, symlinks and junctions, inode/file-ID semantics, long paths, sparse and network files, timestamp resolution, invalid UTF-8, permissions, watcher overflow, and mmap/read behavior. A sleeping placeholder, unconditional fallback, or skipped test must be labeled as an unsupported boundary or completed before capability parity is claimed.

The tenth pass reviews output as a loss-sensitive contract. Trace complete internal results through sorting, deduplication, cursor filtering, hit retention, fisheye preview, context selection, compaction, byte/token ceilings, serializers, sentinels, stderr, and exit status. Verify coordinates against exact source bytes, stable ordering under concurrency, omission and truncation accounting, continuation identity, minimal default telemetry, schema-version compatibility, escaped content, and complete-unit retention. Compare text, JSON, agent, MCP, and report-file projections for semantic parity rather than byte identity. Output economy never authorizes hidden loss or reconstructed coordinates.

The eleventh pass reviews build, dependency, and release provenance. Confirm every compiled C and Zig unit, target feature, generated alias, linker input, optimization mode, LTO choice, and vendored dependency against `build.zig` and `.refs/index.md`. Rebuild from a clean bootstrap state where the round can affect build truth. Distinguish test binaries from the promoted binary and ReleaseSmall from ReleaseFast behavior. Verify artifact hash before and after atomic installation, run the installed binary through the changed consumer path, retain one rollback predecessor, and prove rollback. Repository success does not authorize promotion until installed-path behavior agrees.

The twelfth pass reviews the proof, not merely the presence of tests. Map each invariant and failure mode to a test capable of failing if the implementation is removed or corrupted. Require unit, integration, oracle-parity, adversarial, deterministic-repeat, resource, platform, schema, recovery, clean-build, benchmark, and installed probes in proportion to blast radius. Inspect fixtures for representativeness and independence from the implementation. Reject weakened assertions, tests that duplicate the production algorithm as their oracle, skipped failures, stale snapshots, unbounded hangs, and a targeted green lane presented as whole-suite readiness.

The thirteenth pass reconciles unfinished work and architectural debt. Search current source and ledgers for TODOs, duplicate comments, temporary switches, dead specialists, dormant telemetry, stale route names, abandoned experiments, compatibility shims, oversized owner files, copied request constructors, unresolved test failures, and docs that lead or trail runtime. Every finding must be closed, explicitly retained with owner and trigger, or linked to the canonical pending item. Review is incomplete if the change creates a second owner, leaves newly dead code, hides a prior failure, or adds a TODO without a durable continuation.

The fourteenth pass judges maintainability under the next change. Read the final code as a maintainer who did not witness the round. The owner and invariant should be discoverable from types, boundaries, function-level capability comments, tests, and ledgers without replaying chat history. Reject cleverness whose proof depends on undocumented CPU, compiler, filesystem, or workload assumptions. Prefer the smallest mechanism that preserves the required semantics and measured gain. A performance win purchased with an opaque parallel system is an architectural loss unless its leverage and containment are exceptional and proven.

## Reviewer falsification rules

Do not approve from changed lines alone. Do not approve a declaration, enum, descriptor, import, help entry, or schema as runtime capability. Do not approve a benchmark whose candidate and champion differ in matches, files, route, flags, cache state, binary identity, corpus identity, resource policy, output work, or instrumentation. Do not approve an average when tails or same-binary controls contradict it. Do not approve a timed variant that has not been proven equivalent to the production variant. Do not approve a cache or index hit whose freshness and coverage identity are unknown. Do not approve a silent fallback that changes semantics, resource class, or latency class. Do not approve platform parity from cross-compilation alone. Do not approve a targeted green test while applicable suite failures, skips, or hangs remain unexplained. Do not approve promotion from repository execution alone. Do not approve added complexity because it is theoretically fast; require transferred value on IX workloads and preserved owner clarity.

Every review finding carries severity (`P0` correctness or data loss, `P1` false-negative, security, freshness, release, or severe resource risk, `P2` architectural drift, incomplete capability, material regression, or weak recovery, `P3` bounded maintainability, observability, test, or documentation defect), exact evidence, affected consumer and invariant, causal path, canonical owner, required correction, falsifying proof, and residual risk. The reviewer issues one final verdict: `PASS` when all applicable hard gates and declared margins hold; `REWORK` when an in-scope repair can close the evidence; `EXPERIMENTAL` when knowledge is valuable but runtime adoption is not yet justified; or `BLOCK` when correctness, identity, proof integrity, release safety, or required external state prevents promotion. A verdict without the reviewed route matrix, unresolved findings, and proof receipt is invalid.

The reviewer then performs a removal test in thought and, where cheap, in code: if the new mechanism were disabled, corrupted, stale, or bypassed, which test, telemetry field, health probe, or installed check would detect it? If the answer is none, the capability is not governable. The final handoff states what was reviewed, what was not, why the evidence is sufficient, which risks remain, which pending items were reconciled, whether repository and installed binaries agree, and the single highest-value next review frontier.
