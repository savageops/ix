# Lean Output Schema — Fisheye Preview + Sentinel Strip + JSON Split

## Competitive research findings

Three research threads inform this design:

### ripgrep weaknesses (verified against rg 13.0.0)

1. **No completion sentinel in text mode.** Agent must rely on exit code (0=match, 1=no match, 2=error). Cannot distinguish clean-zero from crash via stdout alone.
2. **`--max-columns-preview` is NOT match-centered.** Shows first N bytes of line + `[... omitted end of long line]` marker. The match may be entirely outside the visible window. (Issue #1078 requested match-centering; never implemented.)
3. **`--max-columns` ignored in `--json`.** JSON consumers get unbounded lines always.
4. **Telemetry baked into JSON.** `elapsed`, `bytes_searched`, etc. always present in `end`/`summary` messages. No "pure results" mode.
5. **`-l`/`-c` output is unsorted.** Parallel traversal = non-deterministic order. Bad for reproducible agent runs.
6. **No column in JSON.** Location is byte offsets (`submatches[].start`). Computing a human column requires UTF-8 decoding.
7. **Disjoint modes.** `--json` mutually exclusive with `-l`/`-c`. Agent picks one surface and loses the others.

### Agent tool convergence (hypergrep, VS Code, ctags)

- **hypergrep** implements L0/L1/L2 tiered detail: ~15 token structural summary → compressed view → full view. 87% token reduction claim.
- **VS Code** separates preview from match geometry (submatch offsets within a preview window).
- **ctags** pioneered "location-only" output: `path:line:kind` with no body. The leanest possible result format.

### Theory (Furnas 1986, Lucene UnifiedHighlighter)

The user's ALOD concept maps to **Furnas's Generalized Fisheye Views (CHI 1986)**: the DOI function `DOI(x|y) = API(x) − D(x,y)` where the match is the focus point `y`, distance `D` is character offset, and `API` (a priori importance) is inversely proportional to line length (long lines skew toward minified/generated content with lower marginal information density per character).

The geometric halving (300→150→75) is a **dyadic-tiered focus+context budget** — structurally analogous to MIP mapping (detail inversely proportional to scale) and binary exponential backoff (r=2 recurrence). This specific combination — line-length-keyed geometric contraction applied to code search previews — does not appear in ripgrep, Lucene/Solr/ES, or the passage-retrieval literature. It's a genuine gap.

**Terminology**: "Fisheye preview" (cite Furnas 1986). The adaptive tiers are the novel component over ripgrep's fixed-radius `--max-columns-preview`.

## Change 1: Fisheye preview (ALOD)

### The DOI model

The match byte position is the **focus point**. Line length acts as the **API modulator**: longer lines carry lower marginal information density (empirical prior over source trees: lines >300 bytes skew toward minified JS, generated tables, data literals). The preview budget contracts geometrically as line length crosses dyadic thresholds.

### Tier schedule

| Tier | Line length (bytes) | Window | What the agent sees |
|------|---------------------|--------|---------------------|
| T0 | ≤ 300 | Full line | Everything — normal source code |
| T1 | 301–600 | Match ± 150 bytes | Match region + nearby context |
| T2 | 601–1200 | Match ± 75 bytes | Tighter match region |
| T3 | > 1200 | Match ± 37 bytes | Minimal match anchor |

Properties:
- The **match substring is always fully visible** — never cut mid-match.
- Truncation marked with `…` at left/right boundaries (UTF-8 safe — `…` is 3 bytes, cheaper than ripgrep's 31-byte `[... omitted end of long line]`).
- Tier thresholds double (300→600→1200), window half-widths halve (150→75→37). The budget is inversely proportional to line length at dyadic breakpoints. This is a reciprocal geometric series.
- For a 5000-char minified line, the preview is ~75 chars centered on the match — a 66× reduction.

### Implementation

**File**: `src/core/search.zig`

Add `fisheyePreview(allocator, line, match_byte_offset, match_len) ![]const u8`:

```zig
const FISHEYE_T0: usize = 300;  // full line below this
const FISHEYE_HALF_WIDTHS = [_]usize{ 150, 75, 37 }; // T1, T2, T3

fn fisheyeTier(line_len: usize) usize {
    if (line_len <= 300) return 0;  // T0: full line
    if (line_len <= 600) return 1;  // T1
    if (line_len <= 1200) return 2; // T2
    return 3;                        // T3
}
```

The function:
1. Computes tier from `line.len`.
2. T0: dupe full line, return.
3. T1–T3: compute window `[match_offset - half_width, match_offset + match_len + half_width]`, clamped to `[0, line.len]`. Allocate result, write `…` prefix if start > 0, copy window, write `…` suffix if end < line.len.

Two call sites (already have `column` as byte offset):
- `recordLineIntoShardImpl` (line ~3858): `.preview = fisheyePreview(allocator, line, column - 1, match_len) catch allocator.dupe(u8, line) catch line`
- `recordLine` (line ~4740): `.preview = try fisheyePreview(allocator, line, column - 1, match_len)`

`match_len` comes from the expression plan. For literals: the literal length. For regex: 0 (regex matches have variable length; the fisheye uses `column` as the anchor point with `match_len=0`, centering the window on the match start).

**Warm-cache**: `writeEscapedWarmQueryField` (search.zig:1487) writes `hit.preview` verbatim. Since preview is fisheye-capped at population, the round-trip preserves the cap. No change needed.

**Inspect path**: `InspectLine.text` / `ContextLine.text` stay untruncated — inspect windows are user-bounded by explicit line ranges. Fisheye applies only to search hit previews.

## Change 2: Lean text sentinel

### Current

`writeSearchReport` (output.zig:308-325) emits ~20 fields + full `hits[]` array:

```
-- ix.result.v1 {"bytes":N,"cmd":"search","dedupe":{...},"expr":"...","access_errors":{...},"files":{...},"matches":N,"ms":{...},"slowest":{...},"hits":[...],"status":"ok"} --
```

### After

```
-- ix.result.v1 {"status":"ok","matches":25,"truncated":false} --
```

Partial:
```
-- ix.result.v1 {"status":"partial","matches":25,"truncated":false,"errors":3} --
```

**Fields kept** (consumer value proven):
- `status` — `"ok"` vs `"partial"`. Agent knows if results are complete.
- `matches` — total match count. Agent detects truncation (matches > hits shown).
- `truncated` — explicit boolean. Currently missing from sentinel. Disambiguates "25 matches, all shown" from "500 matches, 25 shown."
- `errors` — only emitted when `access_errors.total > 0`. Count of unreadable files.

**Fields cut** (zero consumer value):
- `bytes`, `cmd`, `expr`, `dedupe.*`, `files.*`, `ms.*`, `slowest.*`, `access_errors.access_denied`, `hits[]`

### Implementation

Rewrite `writeSearchReport` (output.zig:308-325). The `hits[]` array, telemetry fields, and slowest-path data are removed. The function becomes ~15 lines.

### Gate updates

**`agent-surface-gate-validation.mjs:agentPathContractLane` (lines 205-213)**: currently reads `parsedSearch.value.hits[0].absolute_path` from the sentinel. Update to parse the first text hit line from `search.stdout` (format: `path:line:column:preview`), split on `:` to extract path, join with the known `root`, verify `existsSync`. ~10 line change.

**Zig test `search result sentinel includes agent-safe absolute hit paths` (output.zig:871-922)**: update assertions to check lean fields (`"status":"ok"`, `"matches":1`, `"truncated":false`) and that `hits[]` is absent from the sentinel.

## Change 3: `--json` split from `--stats`

### Principle

ripgrep bakes telemetry into JSON — there's no "pure results" mode. IX splits them.

- `--json` → lean structured output: `{expression, status, matches, truncated, cwd, hits[]}`. Telemetry-free. This is what agents want.
- `--stats` → full telemetry (current `writeSearchJsonReport` body). This is what benchmark/development wants.
- `--json --stats` → both (current behavior). This is what benchmark gates use.
- `--stats-only` → unchanged (text mode, suppresses hits, lean sentinel).

**Invariant**: `--json --stats-only` (every benchmark gate) produces identical JSON to today. Zero benchmark changes.

### Implementation

**`src/cli/args.zig`**:
- Add `stats: bool = false` to `SearchRequest` (after line 46).
- Add `"--stats"` branch in `parseSearch` flag chain (~line 233).

**`src/main.zig`** (search dispatch, lines 107-118):
```zig
if (effective_request.json) {
    if (effective_request.stats) {
        try output.writeSearchJsonReport(stdout, report);  // full telemetry + hits
    } else {
        try output.writeSearchJsonLean(stdout, report);     // lean: expression, status, matches, hits
    }
} else {
    switch (effective_request.output_mode) {
        .normal => if (!effective_request.stats_only) try output.writeSearchHits(stdout, report),
        .files_with_matches => try output.writeFilesWithMatches(stdout, report),
        .count => try output.writeCountPerFile(stdout, report),
    }
    try output.writeSearchReport(stdout, report);  // lean sentinel
}
```

**`src/cli/output.zig`**: Add `writeSearchJsonLean` — extracts the first ~20 lines of `writeSearchJsonReport` (expression, status, cwd, hits[]) and drops the `stats` subtree. Each hit uses `writeSearchHitJson` (path, absolute_path, line, column, preview) — same hit object, just without the 170-field telemetry payload wrapping it.

### Gate impact

**`surfaceParityLane` (agent-surface-gate-validation.mjs:98)**: invokes `search lit:pub src --json --max-hits 2` (no `--stats`). Currently reads `searchValue.stats.matches_found` (line 122). After split, lean JSON has `matches` at top level. Change line 122: `searchValue.stats?.matches_found <= 0` → `searchValue.matches <= 0`.

**All benchmark gates** (`benchmark-runner.mjs:buildIxSearchArgs`, `compare-installed-speed.mjs`, `compare-historical-speed.mjs`, `alternates-decision-table.mjs`): all use `--json --stats-only`. Unchanged path. Zero modifications.
